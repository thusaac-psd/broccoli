# 插件分发

插件从两种来源之一到达每个服务器副本，而 `plugin` 行是整个集群运行哪一种来源的唯一记录（`packages/server/src/plugin_distribution.rs`）：

- 内置（bundle）：`plugin.plugins_dir/<id>/`，随每个节点发布。服务器只读取它，因此发布模板以只读方式挂载。
- 上传（upload）：存放在共享 blob 存储（`packages/common/src/storage`，数据库或对象存储后端）中的插件归档，以其 SHA-256 内容哈希为键。该行的 `archive_hash` 列记录这个哈希。

`archive_hash IS NULL` 表示使用内置版本。非空值表示每台服务器都运行该归档，即使其内置目录中有同一插件 ID。移除上传会清空该列，内置版本随即重新生效。

评测机（worker）不运行任何插件代码。评测器、检查器和比赛类型都在服务器上执行，评测机只运行服务器下发的沙箱操作，因此发布的版本只需到达服务器。出于同样的原因，插件清单中没有评测机部分。

## 发布即一次行写入

`POST /admin/plugins/upload`（`handlers/admin.rs`、`plugin_lifecycle::install`）：

1. `PluginArchive::parse` 校验归档（`plugin_archive.rs`）：压缩后不超过 256 MiB，解压后不超过 512 MiB 且不超过 10,000 个条目；只允许普通文件和目录；只有一个以合法插件 ID 命名的顶层目录；路径分量只能是普通名称；不允许重复文件；`plugin.toml` 可解析且路由和定时器声明合法；清单中的每个路径都在插件根目录内；服务器入口文件存在。
2. 字节写入 blob 存储。`put` 按内容寻址，因此键就是 `parse` 计算出的哈希。
3. 在生命周期锁内，归档被解包到本服务器的缓存，并通过启用和重新加载所用的同一条 `load_then_publish` 路径加载。
4. 只有加载成功后，才会用一次 upsert 写入 `archive_hash`、`is_enabled`、发布的 `version` 与 `content_hash` 指纹，并递增 `generation`。加载失败则不发布任何内容，返回 `422 PLUGIN_LOAD_FAILED`，本服务器继续运行之前的版本。

其他服务器在下一次协调周期（`RECONCILE_INTERVAL`，5 秒）发现新的 generation。不产生任何队列流量：收敛依靠现有的数据库驱动循环，没有变化的周期不做任何文件或 blob 操作。

`POST /admin/plugins/upload/inspect` 只执行第 1 步，返回插件 ID、版本、请求的主机权限以及集群当前在该 ID 下运行的内容，使管理界面在发布前展示权限。

## 在每台服务器上落地

`plugin_distribution::locate` 把该行的来源转换为目录：

- 内置：`plugins_dir/<id>/`，前提是其中有 `plugin.toml`。
- 上传：`cache_dir/<archive hash>/<id>/`。缓存未命中时，服务器获取 blob，拒绝超过上传上限的内容，重新计算 SHA-256 并拒绝不匹配的内容，再次运行 `PluginArchive::parse`（存储中的归档绝不比上传的归档更受信任），检查归档包含预期的插件 ID，然后解包到 `cache_dir/.partial-<hash>` 并重命名到位。因此存在的缓存目录一定是完整的。

`plugin.cache_dir` 属于单台服务器且必须可写；其中没有权威数据，丢失只需为每个上传插件重新下载一次。所有缓存写入和删除都在生命周期互斥锁内进行，因此同一服务器上的解包与清理不会竞争。集群发生变化后，`retain_cache` 删除既未被任何插件发布、也不是任何注册表条目根目录的缓存项。第二个条件保留了在新版本加载失败后仍在服务的旧版本文件：extism 会从 WASM 文件重建池中的实例，Web 资源和翻译也从插件根目录读取。

## 失败与回滚

无法使用已发布内容的服务器（blob 缺失、哈希不匹配、归档无效、`init()` 失败、该服务器禁用了上传）走常规的 `apply` 失败路径：

- 如果它已经在运行该插件，之前的版本继续服务，副本报告 `outdated` 及错误信息。
- 否则报告 `failed`。两种情况下插件都会出现在 `not_ready` 中，`/healthz` 报告 `degraded`，可见性内核对该插件所管辖的范围（记录在 `governs` 列中）失败即关闭。
- 它按退避策略重试。管理员点击重新加载会递增 generation，使所有失败的服务器立即重试。

回滚就是再次发布：上传之前的归档，或移除上传。

## 移除上传

`DELETE /admin/plugins/{id}/upload?expect=bundle_restored|removed`（`plugin_lifecycle::remove_upload`）。结果取决于处理请求的副本的内置目录，而管理员看到的确认信息来自提供详情页的那个副本，因此请求需注明预期的结果；如果本副本会执行另一种结果，则返回 `409 CONFLICT`：

- 处理请求的副本的内置目录中有该插件：一次更新将 `archive_hash` 置为 `NULL`、写入内置版本的指纹并递增 generation。如果插件处于启用状态，会像其他变更一样先在本副本加载内置版本。插件保持原有的启用状态。
- 没有内置版本：删除该行，待触发的定时器一并删除。每台服务器在协调时发现自己应用过的行消失，便遗忘该插件：清除注册内容、移除注册表条目、清理缓存。插件配置和存储行保留，因此再次上传该插件即可恢复其数据。

## 并发保护

发布写入以其预期的来源为条件，因此通过一个副本做出的变更不会悄悄撤销通过另一个副本做出的变更：

- 启用和重新加载只在 `archive_hash` 仍等于处理请求的副本所加载的来源时生效。
- 上传携带 `replaces`，即管理员检查归档时看到的来源（`new`、`bundle` 或归档哈希）。只有预期为 `new` 时才插入新行，只有该来源仍处于发布状态时才更新现有行。
- 移除上传只在同一上传仍处于发布状态时生效。

被拒绝的写入返回 `409 CONFLICT`，并像任何未发布的变更一样把本副本回滚到之前的状态。禁用无需条件：它只改变 `is_enabled`，保留当前发布的来源，因此不会撤销它未曾看到的变更。

## 运维开关

`plugin.uploads_enabled = false` 使两个上传端点都返回 `403 PLUGIN_UPLOAD_DISABLED`，并使该服务器上的 `locate` 拒绝所有上传来源，因此它只运行内置代码，对其余内容失败即关闭。移除上传仍然允许，因为它只会回到内置版本。`GET /admin/plugins/upload` 向管理界面报告该开关。

## 取舍

- 上传和获取时归档都缓存在内存中。大小上限约束了这一点，而且插件相对测试数据很小。
- 其他副本在下一次轮询时获取发布内容，而不是通过推送。这最多带来一个协调周期的延迟，同时热路径上没有新增任何按请求或按周期的开销。
- 在本副本加载失败的上传会在存储中留下其 blob。它按内容寻址且不被任何记录引用，因此无害；删除它会与同一字节的并发上传竞争。
- 某个插件已从集群移除但仍有节点内置它时，该节点会在之后的某次集群变化中重新发现它，并以内置版本重新注册。请保持各节点的内置目录一致。
