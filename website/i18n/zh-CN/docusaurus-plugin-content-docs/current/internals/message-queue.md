# 消息队列

服务器通过 Redis Streams 把沙箱任务交给评测机，评测机也通过它把结果交回。队列位于 `packages/mq`。它不是通用消息代理：其 API 只表达 Broccoli 的三类流转（操作任务、回复、死信），不涉及其他内容。键名、Lua 脚本和时间常量只存在于该 crate 中，因此服务器与评测机不可能对它们产生分歧。

## 承载的流转

| 流转 | 生产者 | 消费者 | 内容 |
| --- | --- | --- | --- |
| 操作任务 | 服务器（`services/operation_batch.rs`） | 任意评测机，或被固定的那台评测机 | `common::worker::Task` |
| 回复 | 执行该任务的评测机 | 发布该任务的服务器 | `common::worker::TaskReply`（`Started`、`Completed`） |
| 死信 | 评测机（毒消息、重试耗尽）、服务器（批次超时） | 任意服务器，写入 `dead_letter_message` 表 | `common::DlqEnvelope` |

Broccoli 在 Redis 中保存的其他内容（节点存活键、取消键、预热 pub/sub 频道、插件状态）都不属于队列。

这些流转对队列的要求：

- 操作任务至少投递一次。被已死评测机取走的任务必须重新执行，而存活评测机正在执行的任务不得被重新执行。
- 回复只送达正在等待它的那一个服务器副本。发往已消失服务器的回复被丢弃，而不是永久保存。
- 不需要优先级，也不需要延迟投递。没有插件设置操作优先级，重试退避只是持有任务的评测机内部的一次休眠。两者都被删除，而不是被实现。
- 任务之间无需顺序。同一批次的操作并行执行，服务器按任务 id 匹配回复。

## 流与键

`<q>` 为 `mq.operation_queue_name`（默认 `operation_tasks`）。节点 id 不含 `:`，因此下列每个键只有一种解析方式。

| 键 | 类型 | 消费组 | 生命周期 |
| --- | --- | --- | --- |
| `<q>` | stream | `workers` | 永久 |
| `<q>:worker:<worker_id>` | stream | `workers` | 其评测机死亡后被排空为止 |
| `<q>:pinned` | 评测机 id 集合 | | 排空后移除成员 |
| `<q>:reply:<server_id>` | stream | 无 | 与服务器存活键的 TTL 相同 |
| `<q>:dlq` | stream | `servers` | 永久 |
| `<q>:heartbeat:<role>:<id>` | string | | 存活 TTL，15 秒（见“存活”） |

每个条目只有一个字段 `p`，保存 JSON 负载。从已死评测机私有流迁出的条目还带有 `n`，即它此前已被投递的次数。

### 工作流与消费组

评测机用一次 `XREADGROUP GROUP workers <worker_id> COUNT <free slots> BLOCK 2000 STREAMS <q>:worker:<id> <q> > >` 同时读取共享流和自己的私有流。消费者名称就是评测机 id，节点声明（`common::node_identity`）保证其唯一，因此重启后的评测机能重新找到自己的待处理条目。每台评测机在启动时以 `XGROUP CREATE ... 0 MKSTREAM` 创建消费组，并把 `BUSYGROUP` 视为成功；起点 `0` 保证在任何评测机存在之前发布的条目仍会被投递。

已投递的条目留在消费组的待处理条目列表（PEL）中，直到评测机结算它。每次结算（确认、转为死信、重新入队）都是一个脚本，先用 `XPENDING <stream> <group> <id> <id> 1 <consumer>` 检查该条目是否仍归这个消费者所有：停顿超过声明阈值的评测机会发现条目已被接管，从而不做任何改动。`XDEL` 使流的长度始终等于积压量加进行中的任务量，因此无需 `MAXLEN` 裁剪；裁剪工作流反而会丢弃未读任务。

### 固定任务

管理员重测可以把提交固定到某台评测机（`target_worker_id`）。服务器用一个脚本发布固定任务：脚本检查该评测机的存活键，然后要么把任务加入 `<q>:worker:<id>` 并把评测机 id 加入 `<q>:pinned`，要么把任务加入共享流。存活检查与写入是同一个原子步骤，因此任务永远不会被路由到已知死亡的评测机，并且无论是否固定，发布都只需一次往返。

若被固定的评测机在发布之后死亡，下一个运行排空脚本的存活评测机（每个回收周期运行一次，见下文）会排空其私有流。若属主的存活键存在，脚本立即返回；否则它把至多 64 个条目迁移到共享流，并在 `n` 中携带其投递次数，私有流清空后删除该流及其在 `<q>:pinned` 中的成员。停顿超过存活 TTL 后恢复的评测机会发现私有流已不存在，在下一次读取时收到 `NOGROUP`，并重新创建消费组。

### 回复流

服务器用普通的 `XREAD` 读取回复流，不使用消费组：回复只对在内存中持有对应等待者的进程有用，把它重新投递给重启后的服务器只会进入 `no_waiter` 分支。每次读取是一次流水线往返：

```text
XDEL <q>:reply:<server_id> <ids the previous read returned>
XREAD COUNT 512 BLOCK 2000 STREAMS <q>:reply:<server_id> <last read id>
EVAL <last-generated-id of the stream>
```

`XDEL` 恰好删除上一次读取返回的条目，因此流中只保留服务器尚未看到的回复，未读条目永远不会被删除。`BLOCK` 在第一次 `XADD` 时即被唤醒，回复无需等待任何轮询间隔。丢失后重建的流按 Redis 时钟生成 id，可能落后于游标；当流的最后生成 id 落后于游标或流不存在时，读取者从头开始读取。

服务器的节点声明拥有回复流（`NodeClaim::own_stream`）：续期存活键的同一个脚本会在流缺失时将其创建为空流（`XADD ... MAXLEN 0`），并赋予它自己的 TTL `REPLY_STREAM_TTL`（10 分钟）；第一次续期在心跳启动时执行，早于服务器发布任何任务。正常关闭时两者都会被删除。因此，崩溃服务器的回复流会在其最后一次续期 10 分钟后按 Redis 时钟过期，无需任何清扫。较长的 TTL 意味着停顿或与 Redis 断开超过 15 秒存活 TTL 的服务器仍会保留期间发布的所有回复。在 TTL 内重启的服务器会读到上一次运行遗留的回复，它们不会到达任何等待者。

评测机用一个脚本发布回复：仅当流存在时才添加回复，否则丢弃：流缺失意味着服务器已消失或丢失了该流。回复永远不会创建流，因此不存在没有 TTL 的流。运行中丢失回复流的服务器（Redis 丢失了数据，或停顿超过 10 分钟）会从重建该流的那次续期得知这一点，并立即让所有未完成的操作失败，使其插件看到失败的操作，而不必等待超时。

## 投递、重新投递与进行中任务的存活

PEL 就是对进行中任务的声明。其空闲时间由 Redis 维护，表示属主上一次证明自己存活距今多久。

- 评测机每 5 秒用 `XCLAIM <stream> workers <self> 0 <ids> JUSTID` 重置其正在执行的每个任务的空闲时间，该命令位于一个脚本中，会跳过已不再归自己所有的 id。`JUSTID` 不计入投递次数。
- 有空闲槽位的评测机每 5 秒在自己的两个流上运行回收脚本：先执行 `XPENDING <stream> workers IDLE 30000 - + <free slots>`，再以同样 30 秒的最小空闲时间执行 `XCLAIM`。`XCLAIM` 的最小空闲时间保证两台评测机同时回收也是安全的：每个条目只会被其中一台取得。
- 只要评测机存活，长时间运行的沙箱任务无论运行多久都不会被回收，因为续期使其空闲时间始终低于 30 秒。崩溃评测机的任务会在其最后一次续期后 30 到 35 秒内被重新投递。

这取代了评测机去重声明（`broccoli:dedup:<task>`）和已死评测机操作回收器。两者存在的原因是旧的消息代理没有 PEL：被弹出的任务存放在无人监视的旁路列表中。有了 PEL，消费组一次只把每个条目投递给一个消费者，并且只有越过空闲阈值才会重新投递，因此存活的评测机保有其任务，死亡的评测机则失去任务。重复执行仍可能在两种情况下发生，且都无害：评测机停顿超过 30 秒（其迟到的结果不会到达任何等待者），以及发布超时后重试、而第一次尝试其实已经成功。

处理器出错（结果在 10 分钟的重试窗口内未能发布）时，任务保持未确认并停止续期，因此它会像崩溃评测机的任务一样被回收。关闭中的评测机立即停止读取，在 30 秒的排空期内完成正在执行的任务，并用一个重新入队脚本（`XADD` 一个副本、`XACK`、`XDEL`）放回已读取但尚未开始的任务，使它们无需等待空闲阈值。

## 重试与毒消息

这里有两个不同的上限。

- 执行重试（`mq.dlq.max_retries`，默认 3）由评测机自己负责：执行失败时由 `common::retry` 带退避地原地重试，最后一次失败会发布一个失败的 `TaskReply::Completed` 和一条 `MaxRetriesExceeded` 死信，然后确认。
- 投递次数（`MAX_DELIVERIES`，3）统计消费组把该条目交出的次数，即 PEL 投递计数器加上 `n`。超过上限的任务每次都令其评测机崩溃或停顿。回收它的评测机不会执行它：评测机发布一个失败回复使服务器停止等待，并以 `RedeliveryExhausted` 将其转为死信。

负载无法解码的任务会立即转为死信（`DeserializationError`）；重试无法修复它。

转为死信是一个脚本：先做所有权检查，再对源条目执行 `XADD <q>:dlq * p <envelope>`、`XACK`、`XDEL`。因此毒消息永远不会滞留在工作流中，也不会在两步之间丢失。服务器在 `servers` 消费组中消费 `<q>:dlq`，在事务中把信封写入 `dead_letter_message`，然后确认。写入失败时条目保持待处理；任何服务器都会在其空闲 30 秒后回收它，因此长达约十分钟的数据库故障只会推迟死信而不会丢失死信。投递 20 次后仍未写入的死信（其写入确定性失败或发生 panic）会以 error 级别完整记录日志并确认，因此不会无限循环。无法解码的信封会被记录日志并确认，因为其他消费者同样无法读取它。管理后台的 DLQ 界面读取的是数据表而不是流。

## 批处理

- 评测机每次循环执行一次 `XREADGROUP`，跨两个流最多返回其空闲槽位数的条目。超出空闲槽位的条目（每个流各自应用 `COUNT`）在本地缓冲区等待，并持续续期。
- 一次 `XREAD` 最多返回 512 个回复。服务器处理一个回复只需微秒级时间（一次映射查找和一次通道发送），因此每台服务器一个读取者足以应对评测机产生的任何突发。
- 每个任务的发布是一次往返（`XADD` 或路由脚本）。操作批次路径已经并发地发出这些请求（`server.operation_batch_publish_concurrency`）。

## 故障行为

- 每条命令都有截止时间。命令连接使用 5 秒响应超时；阻塞读取使用其阻塞时间加 5 秒。因此半开连接表现为超时，而不是挂起。
- 发生超时或 I/O 错误时连接被丢弃，下一条命令以 2 秒连接超时重新连接。错误交给调用方决定是否重试：发布返回 `MqError`，消费循环记录日志、退避一秒后再次读取。
- Redis 重启会关闭所有连接。读取者重新连接并重新发出读取；收到 `NOGROUP` 回复（重启丢失了消费组）时，读取者重新创建消费组并再次读取。服务器的下一次心跳会重建其回复流。

### Redis 崩溃会丢失什么

发布模板以 `appendonly yes` 和 `appendfsync everysec` 运行 Redis，因此崩溃至多丢失最后一秒的写入。对队列而言：

- 在那一秒内发布的任务丢失；其操作等待者超时，卡住任务检测器恢复该提交。
- 在那一秒内丢失的确认会使已执行的任务被重新投递。其第二个结果不会到达任何等待者。
- 在那一秒内丢失的回复按任务丢失的方式恢复。
- 重启后丢失数据（或其存储的 TTL 已过）的 Redis 中不存在回复流：每台服务器的下一次续期会重建其流，并让它正在等待的所有操作失败，插件会立即看到这些操作失败。

### `noeviction` 下的内存

必须设置 `maxmemory-policy noeviction`。每个流条目要么是未读任务，要么是进行中的任务，淘汰会悄无声息地丢弃其中任何一种。Redis 写满时 `XADD` 以 `OOM` 失败，发布返回错误，服务器让该操作批次失败，而不是丢失其任务。已确认的条目立即被删除，每次读取都会删除之前的回复，回复流随其服务器过期，DLQ 流被排入 Postgres，因此内存随实时积压量变化。在出现故障时仍可能增长的流有两个：卡住的服务器的回复流，以及数据库故障期间的 DLQ 流。两者都以 `XADD ... MAXLEN ~ 100000`（`REPLY_STREAM_MAXLEN`、`DEAD_LETTER_MAXLEN`）设置上限，宁可丢弃最旧的条目也不让所有写入停止。共享流从不裁剪，因为那会丢弃排队的任务；当其积压超过 50 000 时服务器会记录错误日志。

## 时钟规则

所有时间比较都基于 Redis 时钟：

- 存活即 TTL 键存在，心跳的年龄为其 TTL 减去 `PTTL`；
- 声明的空闲时间即 PEL 空闲时间；
- 任务的排队等待时间为紧跟在返回它的阻塞读取之后以流水线执行的 Redis `TIME`，减去其条目 id 的毫秒部分。

服务器在自己的单调时钟上测量操作的端到端时间，从发布到收到回复，因此没有任何时间戳跨越节点边界。

## 存活

`common::liveness` 持有唯一的定义：键 `<q>:heartbeat:<role>:<id>` 存在期间节点即存活（位于队列基础名之下，因此在同一个 Redis 中使用不同名称的部署永远看不到彼此的节点）。该键 TTL 为 15 秒，节点每 3 秒续期一次，每次续期的截止时间为 5 秒，因此少数几次缓慢的续期不会使其过期；它同时也是节点的 ID 声明。系统仪表盘、固定路由脚本和私有流排空脚本都向这同一个键询问这同一个问题。评测机的进行中任务完全不使用它：其 PEL 空闲时间回答了属主是否存活。回复也不使用它：回复流有意比存活键存活得更久。

## 可观测性

服务器的队列深度采样器（`handlers/system.rs`）通过一次脚本调用报告每个流：共享流、DLQ 流和每台存活评测机私有流的 `unread`（尚无消费者取走的条目）与 `pending`（PEL 大小），以及服务器自身回复流的长度。它们输入 `broccoli_mq_queue_depth` 和 `GET /api/v1/system/queues`。评测机统计重新投递次数（`broccoli_mq_redeliveries_total`，按流角色标注）和死信数（`broccoli_dlq_messages_total`），并根据条目 id 记录排队等待时间（`broccoli_mq_message_age_seconds`）。

## 不支持的部署

脚本会同时操作多个键，因此队列需要单个 Redis 实例或带副本的主节点，而不是 Redis Cluster。
