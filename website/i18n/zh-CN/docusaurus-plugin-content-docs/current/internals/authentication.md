# 身份认证

已登录的客户端持有一个短期的访问令牌，即以 `Authorization: Bearer` 发送的 JWT，以及一个长期的刷新令牌，用于换取新的访问令牌（使用 HttpOnly Cookie 调用 `POST /auth/refresh`，或在请求体中携带令牌调用 `POST /auth/cli-refresh`）。每个访问令牌都由 `services::auth_tokens::issue_access_token` 根据用户在数据库中的当前角色和权限签发。

## 会话

每次登录都是一个会话，即 `auth_session` 中的一行：登录会开启一个会话，设备流授权同样会开启一个。每个访问令牌都指明其所属会话（`sid` 声明），每个刷新令牌都属于一个会话。刷新保持原会话不变，`POST /auth/cli-token` 会在调用者的会话中新增一个刷新令牌。

会话在以下情况下结束：

| 事件 | 结束的会话 |
| --- | --- |
| `POST /auth/logout` | 刷新 Cookie 所属的会话，以及持有者令牌指明的会话 |
| 已轮换的刷新令牌在宽限期之后被重放 | 该令牌所属的会话 |
| 管理员重置密码、授予或撤销该用户的某个角色，或删除账户 | 该用户的全部会话 |

结束会话会同时删除其全部刷新令牌，以及它已授权但 CLI 尚未领取的设备码。用户在其他浏览器或 CLI 中的其他会话保持登录。没有 Cookie 的客户端（例如 CLI）通过发送访问令牌退出登录。

## 开启会话

会话建立在一次检查之上：登录所验证的密码，或授权设备码的那个仍然有效的会话（`device_authorization.approved_by`）。检查发生在会话创建之前，因此密码重置、角色变更或账户删除可能在两者之间提交。`services::auth_tokens::open_session` 是开启会话的唯一途径，它接收所检查的内容（`SignIn`），并在插入会话行的同一条语句中、持有用户行共享锁的情况下再次检查：

| 凭据变更 | 结果 |
| --- | --- |
| 登录到达时变更已持有用户行 | 登录等待，随后发现密码已被替换或授权会话已结束，不开启任何会话：登录返回 `401 INVALID_CREDENTIALS`，设备轮询返回 `expired_token` |
| 登录持有用户行时变更到达 | 变更等待登录提交，然后连同该用户的其他会话一起结束新会话 |

每次凭据变更都先锁定用户行（所有者锁，`refresh_token::LOCK_OWNER_SQL`），再锁定会话行；登录按同样的顺序加锁，因此两者不会死锁。出于同样的原因，设备轮询会先锁定授权用户的行，再锁定设备码自身的行。

设备码的授权属于授权它的会话：外键 `approved_by` 会随会话一起删除授权，因此授权永远不会比给出它的浏览器登录存活得更久。

## 新鲜度

当令牌所代表的内容终止时，令牌即失效：其会话结束，用户的密码、角色或账户发生变更（`user.credentials_changed_at`），或用户被删除。`extractors::auth::fresh_user` 是唯一的检查，仅需一次索引读取。失效的令牌返回 `401 TOKEN_INVALID`，客户端随即刷新，获得反映用户当前所持权限的令牌。

哪些请求需要承担这项检查，由请求方法决定：

| 请求 | 检查 |
| --- | --- |
| 核心路由上的 `POST`、`PUT`、`PATCH`、`DELETE` | `fresh_user`，经由 `AuthUser` |
| 核心路由上的 `GET`、`HEAD` | 仅校验签名和有效期 |
| `GET /auth/me` | `fresh_user`，经由 `FreshAuthUser` |
| 插件路由（`/p/...`）上的任意方法 | `fresh_user`，在代理中执行 |

`AuthUser` 依据请求方法作出判断，因此修改状态的路由的处理函数无法通过选用开销更小的提取器绕过检查；提交、运行代码以及其他消耗配额或修改状态的请求，都会在处理函数运行之前拒绝失效的令牌。集成测试 `every_state_changing_route_refuses_a_stale_token` 会向 OpenAPI 文档中每个需要认证的修改类操作发送失效令牌。

读请求保持无状态路径，因此热点读路由在认证时不访问数据库。失效的令牌（包括已退出登录的令牌）因此最多还能读取一个访问令牌有效期，即 `jwt::ACCESS_TOKEN_TTL`（5 分钟）。需要依据调用者当前账户作答的读请求使用 `FreshAuthUser`。
